Two more findings in the API:

- The archive table's version carried the newest `fpa_games.created_at`, and
  every weekly ingest deletes and rewrites the baseline season's rows. So the
  2025 fragment's ETag moved every week with nothing changed. Harmless before
  (nothing listened), but a publication check keyed on it would purge /2025/
  weekly. Fixed: the archive version is a hash of the figures it prints.
- The fragment version did not carry the archive season list the season
  switcher prints. Fixed: it does now (`|as<seasons>`).

## The fix

### API (`artifacts/api-server`)

- `GET /embed/fpa/version` (`src/routes/fpa.ts`): per season (the current one
  and each archive), the six `format-view` fragment ETags, one version over
  them, `kind`, `weekNumber`, `updatedAt`, `teams`; and one version over all
  seasons. Rendered through the same `fragmentOptions(req)` as `/embed/fpa`,
  so for the plugin's own request origin the ETags are exactly the fragments'
  (tested). `no-store`, under `/embed/` (the embed key guards it). Cheap: the
  tables are memoized and each render is cached on its version; no database
  read unless an ingest just dropped the memo. A season whose table is
  missing answers 503, which the plugin reads as "nothing to publish".
- `fpa-data.ts`: archive version = season, format, view, rows, through-week,
  content hash. `fpa-ssr.ts`: archive seasons in the fragment version; LRU 24
  to 48 (two origins x 12 renders x the standalone page).

### Plugin (`wordpress-plugin/statchasers-news`)

`statchasers-fpa-cache.php` (new, loaded after the edge helpers), the stats
and depth-chart pattern on the shared `statchasers-edge-cache.php`:

1. Every 5 minutes (`statchasers_fpa_publish_check`, shared
   `statchasers_five_minutes` schedule) read `/embed/fpa/version`. A season
   is changed when its version (or kind: the rollover) differs from the
   record `statchasers_fpa_published`, or on a forced run.
2. For every changed season fetch all six fragments uncached
   (`statchasers_fpa_remote`) and check each ETag against the announced one.
   **Any** failure (HTTP, empty body, an ETag that moved) ends the run with
   nothing written: transients and backups untouched, no WP Rocket clean, no
   purge, record unchanged; the next run tries again.
3. Write them as the fresh copy and backup under the shortcode's own keys
   (`statchasers_fpa_cache_keys`, shared with `statchasers_fpa_fetch`).
4. `rocket_clean_files()` for the changed seasons' addresses (WP Rocket's
   per-URL clean deletes the directory, desktop + mobile files; on the host
   it is recursive, so the base clean also drops /2025/'s file, which simply
   re-renders from its unchanged transient).
5. Then the edge (`statchasers_edge_publish`): per season the address and 17
   query variants (each format and each view alone, defaults spelled out, and
   every pair in both orders: the links before 11-26 wrote `format=ppr`, after
   it `format=half`), 18 paths, through `CDN_Clear_Cache_Api::cache_api_call`,
   with the retry ledger (5, 10, 20, 40, 80 minutes, six attempts).
6. Record, and a minute later warm each purged address as a desktop and as a
   phone (`statchasers_fpa_warm`); an address whose purge failed is warmed by
   the retry once it lands.

The archive is touched only when its own version moves (a historical
correction); the weekly ingest purges the current season's 18 paths and
nothing under /2025/.

Edge lifetime headers (`statchasers_edge_ttl_headers`, on `template_redirect`
20, after the season 301s and never on a 404): the current page asks for 6 h
(`STATCHASERS_EDGE_TTL`, as the stats pages), the archive for 30 days, with
`X-SC-FPA-Cache: edge-ttl=N; season=current|2025; published=<version>`.

By hand: `wp eval 'print_r( statchasers_fpa_publish_check( true ) );'`
republishes every season even when nothing changed.

`statchasers-edge-cache.php`: `statchasers_fpa_published` joins the records a
retry warm-up may write (the SOS branch adds its own line at the same spot: a
one-line merge).

## Effective public TTL

Still the edge's: Rocket.net strips the origin's Cache-Control and stamps
`s-maxage=2592000` (30 days) on every 200, and mak cannot change those rules.
The 6 h and 30 d headers this branch sends are statements of intent only.
What bounds staleness is the targeted purge: a new dataset served by the API
reaches the edge within one WP-cron interval (5 minutes) plus the warm-up
minute, or after the retry schedule (up to about 2.5 hours across six
attempts) when the purge API refuses. If the check cannot run at all (cron
stopped, API version endpoint down), the page stays as stale as before: up to
30 days at the edge.
