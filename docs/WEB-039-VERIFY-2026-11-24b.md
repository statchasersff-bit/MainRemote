## What already worked (WEB-039 as shipped)

There is one resolver, `gameAvailability` (matchup/availability.ts), keyed on the game's season and week:

- The preview runs it through `gameRoster`.
- Player pages run it through `currentStatus` (player/current-status.ts) for the club's next game. The header, Outlook, Injury tab and FAQ all read `PlayerPageData.designation`, `currentStatus`.

Each result carries the designation, source (`nfl-report` / `sleeper` / `reserve` / `none`), the report's state and `fetchedAt`, and the game week. These rules held:

- A game that is not the club's next one gets no designations (`nextGame: false`, reserve lists stand), so an older preview cannot pick up today's status.
- The Injury Watch count and rows derive from one `listing` field.
- The "If he sits" advice and the preview-fantasy "monitor" items fire only for rows with a current status. Pending means the player missed the last game, and that row says "has no Week N status yet".
- Practice lines stay apart from game status.
- `weekReport` turns final on any game status, or on a read within 30 h of kickoff. That covers Thursday, Monday and post-bye weeks, because the last club game comes from the logs, so byes are skipped.

## What this pass changed

1. **Injury tab card sentence** (`player/injury-tab.ts` `statusAnswer`). With no final report it said "No injury designation for Week 12 at the Rams.", which reads as a published report. It now says "No game designation yet for Week 12 at the Rams." until the report is final. The FAQ already used the approved "yet" wording.
2. **Preview Injury Watch** (`matchup/preview.ts`, `preview-premium.ts`).
   - Each column's count now names the report it stands on: "report as of Nov 24", "Week 12 report not out yet" or "Week 12 game statuses not out yet". The phones' bar does the same when both clubs agree.
   - The footer "No other 5%+ rostered Rams carry a designation." prints only under a final report. Before that it reads "...have a Week 12 game designation yet."
   - The clean-sheet note no longer says "every role in the Usage Report is available" before the report is final.
   - `Preview.injuryReports` carries each club's report state and read time.
3. **Cache key** (`team/team-data.ts` `dataVersion`). The key now includes `practiceStamp(season)`, so an evening report read re-renders the team hub's injury list and, through `matchupVersion`, every matchup page. Before this, nothing in the matchup or team keys moved on a report-only change. Locally the change still showed up, because the matchup ETag varied between identical requests here (odds and news fetches failing offline). Production, with those inputs cached, could have held the old Injury Watch and answered 304. Player pages already keyed on `practiceStamp` and the designation.

## Refresh path

The production path is `refreshPracticeReports()` (player/live-refresh.ts): the builder rewrites `practice_reports/<season>.json`, then `invalidatePlayerRenderCache()`.

The test simulated the builder's write in place under a running production-mode server (`NODE_ENV=production`, live refresh off). Fixture: St. Brown Questionable → no status, same Week 12. Result:

- Preview row, the Lions count (1 → 0 designated), the advice sentence, the header, Outlook and the Injury tab all changed on the next request.
- The report date moved with them.
- The player page ETag changed (designation + practice stamp). The matchup ETag changed too.

Stale surfaces: none observed. The one place an old value could survive was the matchup and team fragment cache (and the ETag/304 behind it). Item 3 closes that.
